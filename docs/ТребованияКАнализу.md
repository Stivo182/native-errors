# Требования к анализу нативных ошибок

## 1. Термины и область действия

### 1.1. Назначение

Анализатор получает реальную `ИнформацияОбОшибке` OneScript и пытается классифицировать нативную ошибку в один из публичных кодов `native-errors`.

Примеры существующих кодов:

```text
network.connection_refused
network.name_resolution_failed
filesystem.not_found
```

В требованиях и тестах запрещено использовать несуществующие публичные коды как будто они уже входят в контракт библиотеки.

Если требуется обсуждение еще не существующего кода, он должен быть явно помечен как:

```text
гипотетический код
```

Нельзя подменять одну семантику похожим существующим кодом. Например сетевой timeout нельзя классифицировать как `http.operation_timed_out`, если фактически не установлено, что произошел именно HTTP timeout.

### 1.2. Классификация

Классификация — детерминированное преобразование:

```text
ИнформацияОбОшибке
        ↓
анализ доступных кадров и признаков
        ↓
один публичный код native-errors
```

или:

```text
Неопределено
```

если достаточных оснований нет.

### 1.3. Кадр ошибки

Кадр — одна логическая ошибка в цепочке причин.

Условно:

```text
Кадр 0
└── Кадр 1
    └── Кадр 2
```

Для каждого кадра признаки анализируются совместно только внутри этого кадра.

### 1.4. Восстановленный кадр

Восстановленный кадр — кадр, полученный не непосредственно из структурированной цепочки `Причина`, а из формата `ПодробноеПредставлениеОшибки` или другого текстового представления OneScript.

Восстановленный кадр всегда считается менее надежным источником, чем эквивалентный структурированный кадр.

---

# 2. Допустимые входы и модель кадров

## 2.1. Публичный вход

Публичный фасад классификации принимает:

```bsl
ИнформацияОбОшибке
```

а не произвольную строку.

Не поддерживается API вида:

```bsl
Классифицировать("Connection refused")
```

Строковые представления могут анализироваться только как часть полученной `ИнформацияОбОшибке`.

## 2.2. Цепочка причин

Анализатор должен обработать всю доступную цепочку:

```text
ИнформацияОбОшибке
└── Причина
    └── Причина
        └── ...
```

Но глубина кадра сама по себе не задает его приоритет.

Запрещено правило:

> Самая глубокая ошибка является правильной классификацией.

## 2.3. Независимый анализ кадров

Каждый кадр сначала преобразуется во внутреннее представление:

```text
Кадр
    Структурированные свойства
    Параметры
    Доступный тип
    Машинные коды
    Описание
    Происхождение
    Глубина
```

Анализатор не должен сначала склеивать всю цепочку в одну строку.

## 2.4. Запрет склейки признаков разных кадров

Все признаки одного правила должны быть подтверждены одним и тем же кадром.

Недопустимо:

```text
Кадр A:
    тип = SocketException
    текст = посторонний

Кадр B:
    тип = другой
    текст = Connection refused
```

и после этого:

```text
SocketException
+
Connection refused
→ network.connection_refused
```

Результат такого анализа должен быть:

```text
Неопределено
```

если ни один отдельный кадр не удовлетворяет правилу полностью.

API внутренних распознавателей должен либо:

- выполнять комбинированную проверку одного кадра;
- либо возвращать объект найденного совпадения, привязанный к конкретному кадру.

Отдельные глобальные проверки вида:

```text
СодержитТип(...)
СодержитФрагментСообщения(...)
```

не должны использоваться для построения одного результата без проверки принадлежности одному кадру.

# 3. Уровни надежности признаков

Признак используется только если он действительно доступен через полученную `ИнформацияОбОшибке` либо достоверно восстановлен из документированного формата OneScript.

Нельзя проектировать правила, исходя из того, что `errno`, CLR type, SocketError или другое свойство теоретически существуют внутри .NET, если они фактически не доступны анализатору.

## 3.1. Уровень A — структурированный стабильный признак

Наиболее сильные признаки:

```text
уже нормализованная ошибка native-errors;
структурированная ошибка oscript-errors;
явный машинный код, доступный через ИнформацияОбОшибке;
структурированное специализированное свойство.
```

Если такой признак однозначно задает классификацию, текстовая эвристика не должна быть обязательной.

## 3.2. Уровень B — структурированная комбинация признаков

Например:

```text
достоверный тип исключения
+
машинный параметр
```

или другая комбинация реальных структурированных данных одного кадра.

## 3.3. Уровень C — структурный контекст плюс текст

Например:

```text
достоверно известный тип кадра
+
точный подтвержденный фрагмент сообщения
```

Такое правило сильнее чистого текстового совпадения.

## 3.4. Уровень D — восстановленные признаки

Признаки, извлеченные из `ПодробноеПредставлениеОшибки`.

Например строка:

```text
Внешнее исключение (System.Net.Sockets.SocketException)
```

может позволить восстановить предполагаемое имя .NET-типа.

Но это:

```text
восстановленное имя типа из текста
```

а не:

```text
структурированное свойство типа исключения
```

Поэтому оно имеет меньшую силу.

## 3.5. Уровень E — чистый текстовый признак

Точный известный текст или фрагмент сообщения без дополнительного структурированного подтверждения.

Это fallback-уровень.

Не допускаются:

- fuzzy matching;
- расстояние Левенштейна;
- семантическое сходство;
- LLM-классификация;
- приблизительное определение причины.

# 4. Алгоритм выбора результата

Алгоритм выбора должен быть публично определен и не зависеть от случайного порядка встроенных правил.

## 4.1. Уже нормализованная корневая ошибка

Если корневая ошибка уже является нормализованной ошибкой `native-errors`, она возвращается без повторной классификации.

## 4.2. Пользовательские классификаторы

Пользовательские классификаторы являются явным override-механизмом.

Они выполняются:

```text
в порядке регистрации
```

Первый пользовательский классификатор, вернувший результат, завершает классификацию.

Порядок пользовательских классификаторов является частью публичного контракта.

## 4.3. Структурированные коды native-errors

До текстовой классификации анализатор собирает из всех кадров коды из
[`КодыНативныхОшибок`](КодыНативныхОшибок.md).

```text
0 уникальных кодов  → продолжить классификацию
1 уникальный код    → вернуть этот код
2+ разных кодов     → Неопределено
```

Корневая ошибка с собственным кодом возвращается без дальнейшего анализа.

Чужой структурированный код запрещает встроенную текстовую классификацию только
своего кадра. Его причины продолжают анализироваться. Пользовательские
классификаторы и декларативные правила получают такой кадр без ограничений.

## 4.4. Встроенные классификаторы

Для встроенных правил порядок регистрации не должен разрешать семантический конфликт.

Все подходящие встроенные правила формируют внутренние кандидаты.

Состав внутренних кандидатов не входит в публичный контракт.

## 4.5. Сравнение по надежности

Первым критерием является уровень надежности признаков.

Например:

```text
A > B > C > D > E
```

Кандидат более высокого уровня побеждает кандидата более низкого уровня.

## 4.6. Сравнение по специфичности

Если кандидаты имеют одинаковую надежность, применяется явно определенное отношение специфичности.

Например, если каталог формально устанавливает:

```text
A является более специфичным вариантом B
```

то выбирается `A`.

Специфичность не должна выводиться автоматически из:

- длины кода;
- количества точек в имени;
- глубины кадра;
- порядка правил;
- длины текста.

Отношение специфичности должно быть явно задано.

## 4.7. Одинаковый код

Если несколько кадров или правил независимо приводят к одному коду:

```text
network.connection_refused
network.connection_refused
```

это не конфликт.

Результатом является:

```text
network.connection_refused
```

## 4.8. Неоднозначность

Если остаются два разных кандидата:

```text
код A
код B
```

которые:

- имеют одинаковую надежность;
- не находятся в отношении специфичности;

результат:

```text
Неопределено
```

Глубина кадра не разрешает такой конфликт.

Порядок встроенных правил также не разрешает такой конфликт.

# 5. Текстовые правила и происхождение вариантов

## 5.1. Runtime-доказательство обязательно

Production-rule, основанный полностью или частично на тексте, допускается только при наличии подтвержденного runtime-case.

Для каждого текстового варианта должны быть известны:

```text
воспроизводящий тест либо сохраненный runtime-case;
версия OneScript;
операционная система;
runtime .NET;
локаль;
способ получения:
    прямое исключение
    или ПодробноеПредставлениеОшибки;
положительный сценарий;
близкий отрицательный сценарий.
```

Слово «желательно» здесь не используется.

Это обязательное условие добавления production-rule.

## 5.2. Источники кандидатов

Инструменты вроде:

```text
source-error-summary
```

могут:

- находить потенциальные сообщения;
- подсказывать возможные типы;
- помогать искать reproducer.

Но они не являются доказательством production-rule.

### 5.2.1. Продолжение инвентаризации

Текущая очередь кандидатов строится командой:

```powershell
probes\source-error-worklist.ps1
```

Она читает только `source-error-report.json` и `source-error-review.json`, не сканируя исходники OneScript.
После рассмотрения сигнатуры ее результат фиксируется в журнале по полям `File`, `ExceptionType` и
`Statement`. Повторный анализ исходников нужен только после явного обновления инвентаря.

## 5.3. Точный текст предпочтительнее общего слова

Плохое самостоятельное правило:

```text
refused
```

Лучше:

```text
Connection refused
```

Еще лучше:

```text
контекст конкретного кадра
+
Connection refused
```

## 5.4. Общие слова

Слова вроде:

```text
refused
timeout
certificate
reset
```

могут использоваться для предварительного отбора кандидатов.

Они не должны сами по себе задавать итоговый код.

## 5.5. Regex

Регулярное выражение применяется только когда нужно:

- извлечь переменную структурированную часть;
- извлечь код;
- распознать подтвержденный формат runtime.

Regex является деталью реализации и не входит в публичный контракт.

# 6. `ПодробноеПредставлениеОшибки`

## 6.1. Источник

Публичный фасад по-прежнему получает:

```bsl
ИнформацияОбОшибке
```

а не строку подробного представления.

## 6.2. Оборачивающая ошибка

`ПодробноеПредставлениеОшибки` может находиться внутри описания оборачивающей `ИнформацияОбОшибке`.

Анализатор может восстановить из него дополнительные кадры.

## 6.3. Происхождение восстановленных кадров

Каждый восстановленный кадр должен быть помечен как:

```text
текстово восстановленный
```

и иметь меньший приоритет, чем эквивалентный непосредственно доступный структурированный кадр.

## 6.4. Нельзя выполнять глобальный поиск

Запрещена схема:

```text
взять все ПодробноеПредставлениеОшибки
→ найти где-нибудь SocketException
→ найти где-нибудь Connection refused
→ объединить признаки
```

Сначала должна быть восстановлена структура отдельных кадров.

После этого признаки анализируются внутри каждого восстановленного кадра отдельно.

## 6.5. Порядок кадров

Порядок должен восстанавливаться из фактического формата `ПодробноеПредставлениеОшибки`.

Нельзя использовать эвристику:

> Последний exception в тексте — главный.

## 6.6. Паритет сценариев

Каждый поддерживаемый сценарий, если технически возможно, должен проверяться двумя способами:

```text
реальная прямая ИнформацияОбОшибке
```

и:

```text
та же ошибка внутри обертки с ПодробнымПредставлениемОшибки
```

Код классификации должен совпадать, если обертка не добавляет более сильную семантику.

# 7. Тестирование и совместимость

## 7.1. Реальные ошибки

Основной production-rule должен подтверждаться реальным вызовом платформенного API либо сохраненным подтвержденным runtime-case.

Мок текста не является достаточным доказательством.

## 7.2. Обязательные негативные тесты

Для каждого текстового правила требуется близкий отрицательный сценарий.

Обязательно иметь тест на разнесенные признаки:

```text
Кадр A:
    подходящий тип
    неподходящий текст

Кадр B:
    неподходящий тип
    подходящий текст

Ожидается:
    Неопределено
```

## 7.3. Конфликт встроенных кандидатов

Проверить:

```text
разные коды
одинаковая надежность
нет отношения специфичности
```

Ожидается:

```text
Неопределено
```

## 7.4. Одинаковые кандидаты

Несколько кадров дают один код.

Ожидается этот код, конфликт отсутствует.

## 7.5. Пользовательский приоритет

Проверить:

```text
пользовательский классификатор
+
встроенное правило
```

Пользовательский классификатор должен победить согласно порядку регистрации.

## 7.6. Уже нормализованная ошибка

Повторная классификация уже нормализованной корневой ошибки не должна изменять ее.

## 7.7. Матрица окружений

Для runtime-case фиксируется локаль.

```text
локаль
```

Локальная проверка русской и английской локалей выполняется из каталогов с
соответствующим `oscript.cfg`:

```powershell
Push-Location tests\locales\ru
oneunit execute -f ..\..\ТестыКлассификатораНативныхОшибок.os --mode summary
Pop-Location

Push-Location tests\locales\en
oneunit execute -f ..\..\ТестыКлассификатораНативныхОшибок.os --mode summary
Pop-Location
```

Проверка других версий OneScript, ОС и .NET runtime в эту матрицу не входит.

# 8. Производительность

Производительность должна измеряться на фиксированном benchmark-наборе.

## 8.1. Обязательные сценарии

Benchmark должен включать:

### B1. Уже нормализованная ошибка

Проверка быстрого выхода.

### B2. Известное правило раннего семейства

Типичный быстрый успешный сценарий.

### B3. Известное правило последнего семейства

Успешный сценарий с большим объемом поиска.

### B4. Неизвестная короткая ошибка

Worst-case для короткого входа.

### B5. Неизвестная длинная цепочка

Worst-case обхода нескольких кадров.

### B6. `ПодробноеПредставлениеОшибки`

Измерение стоимости восстановления кадров и дальнейшей классификации.

### B7. Пользовательские классификаторы

Измерение накладных расходов extension pipeline.

## 8.2. Baseline

Для каждого benchmark фиксируется baseline:

```text
версия native-errors;
версия OneScript;
ОС;
.NET runtime;
число итераций;
медиана;
при необходимости p95.
```

## 8.3. Регрессия

До получения первого baseline абсолютный норматив не задается.

После фиксации baseline изменение считается performance-regression, если оно превышает согласованный относительный порог при сопоставимом окружении.

Рекомендуемый начальный порог для CI:

```text
+20% к медиане
```

при условии достаточного числа итераций и устойчивого результата.

Порог должен быть подтвержден практическими измерениями и может быть скорректирован.

## 8.4. Оптимизация

До появления измеряемой проблемы не вводить заранее:

- trie;
- Aho-Corasick;
- сложные текстовые индексы;
- счетчики частот;
- специализированные поисковые автоматы.

Сначала:

```text
benchmark
→ обнаруженная регрессия
→ локализация причины
→ минимальная оптимизация
```

# 9. Ограничения

Библиотека не гарантирует классификацию любого исключения OneScript.

Если runtime предоставляет только неоднозначный текст и нет достаточного набора подтвержденных признаков:

```text
Неопределено
```

является корректным результатом.

False positive считается более серьезной ошибкой, чем отсутствие классификации.

Стабильным контрактом библиотеки являются публичные коды `native-errors`, а не:

- тексты OneScript;
- сообщения .NET;
- regex;
- имена внутренних правил;
- порядок встроенных классификаторов;
- формат внутренних кандидатов.

Основной инвариант:

> Встроенная классификация возвращает код только тогда, когда один кадр содержит достаточный подтвержденный набор признаков, а формальный алгоритм выбора не оставляет неразрешенной неоднозначности.
